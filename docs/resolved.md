## PROWL-026 / P6-003: `prowl doctor` — Environment Health Check (code-complete on branch)
**Status**: Code-complete on 2026-09-11 (branch prowl-doctor); pending PR merge and release.
**Description**: Added `prowl doctor`, a command that verifies the environment is ready to run hunts and prints a color-coded report (green ✓ pass / red ✗ fail / yellow ⚠ warn / gray ○ skip) with a one-line summary and a CI-friendly exit code (0 when nothing failed — warnings are acceptable — 1 on any failure). Each check is a pure function `{ name, status, message, fixable }` over an injected `DoctorDeps` seam (Node version, platform, cwd, env, Playwright probe, command runner, config loader, macdriver status, and the two fixers), so 31 new unit tests cover every pass/fail/warn/skip/fix path without touching the real system (1148 tests total, from 1117; lint + tsup/DTS build green). ## PROWL-056 / ARCH-008: Event-driven AX waits via AXObserver (code-complete on branch)
**Status**: Code-complete on 2026-09-10 (branch macdriver-axobserver-waits); pending PR merge and release.
**Description**: The `prowl-macdriver` Swift helper waited by polling on a fixed 100ms tick (`waitFor` looped on `usleep`, and menu-open detection in `openMenu`/`clickMenu` polled the status item's children). Both now use a **hybrid, event-driven wait** (the WebDriver BiDi lesson applied to macdriver): one immediate predicate check, then subscribe to the attached app's `AXObserver` notifications and re-run the predicate whenever one fires, with a **slow 1s safety re-poll** kept underneath because AX apps routinely fail to announce a change. A new pure module **`macdriver/Sources/prowl-macdriver/AXEventWaiter.swift`** owns this: it creates a per-pid `AXObserver`, registers a broad best-effort notification set (`AXWindowCreated`, `AXUIElementDestroyed`, `AXFocusedUIElementChanged`, `AXValueChanged`, `AXMenuOpened`/`AXMenuClosed`, `AXCreated`, `AXLayoutChanged`, `AXRowCountChanged`, `AXSelectedChildrenChanged`), adds the observer's run-loop source to the command thread's own `CFRunLoop`, and pumps it with `CFRunLoopRunInMode` for the duration of the wait — the helper is a synchronous stdio command loop, so the wait blocks helper-side exactly as before, just waking on notifications instead of a timer. The observer is torn down (source removed, notifications unregistered) when the wait completes so nothing leaks across commands. **Registration is best-effort per notification** (`kAXErrorNotificationUnsupported` is expected, never fatal); when *no* notification registers, the wait **degrades to the classic 100ms poll** and reports `"waitMode":"polling"` in the response (`"event"` otherwise). **Timeout preserved exactly** — a wait that never resolves still errors at its deadline with the same message. The wait loop is factored into a pure `AXEventWaiter.drive` seam (injectable clock + register/teardown/pump/sleep) so the immediate-resolve, event-resolve, degraded-poll, both timeout branches, and long degraded deadlines are unit-tested deterministically with a manual clock, plus `Session.waitFor` and menu-open tests for response shape, event emission, and timeout behavior. **Protocol change:** the stdio protocol gained **server-initiated event lines** — a JSON object with an `event` discriminant and **no `id`**, distinct from id-matched responses — emitted once per AX notification received during a wait (`{"event":"axNotification","cmd":"waitFor","notification":"AXMenuOpened"}`). `SpawnMacHelperClient` (`src/browser/mac-helper.ts`) routes these out-of-band in `dispatch` before the id lookup so they never touch the pending-request map, forwarding them to an optional `onEvent` sink; sink failures report a diagnostic containing the event name and error without breaking transport. When no sink is provided, events are dropped. **No behavior change to hunt semantics** — same steps, same results, lower latency and fewer timing races; the macOS target stays experimental and the TS `MacDriver` surface is unchanged. Scope was limited to `waitFor` and the menu-open detection path; no other helper verbs touched, no new dependencies. Coverage: 6 new pure `AXEventWaiter.drive` Swift tests (`macdriver/Tests/ProwlMacDriverCoreTests/AXEventWaiterTests.swift`), 6 new `Session` wait/menu Swift tests, and 4 new end-to-end TS event-routing tests through a real subprocess (interleaved event before response, malformed event noise ignored, no-sink drop, throwing-sink diagnostic containment). `swift build -c release` + `swift test` green (47 Swift tests); TS `npm run build` + `npm run lint` clean; 1117/1117 TS tests pass. macdriver protocol README documents the event lines and event-driven waits. **No macdriver version bump on this branch** — the pinned `MACDRIVER_VERSION`/helper pin is bumped at release time per `macdriver/RELEASING.md`; this helper change ships with the next `macdriver-v*` release. **Not verified here** (repo no-live-app policy): live latency against a real macOS app is the owner's dogfood step.

## ~~PROWL-051 / ARCH-005: Arbitrary key support for `press` on macOS~~
**Resolved**: 2026-09-03 (branch macos-press-keys)
**Description**: The `prowl-macdriver` Swift helper's `press` verb mapped only Enter/Return/Space onto `AXPress` and rejected every other key; it now synthesizes real keystrokes so `press` on macOS accepts the same vocabulary as the web (Playwright) target. A new **pure** parser (`macdriver/Sources/prowl-macdriver/KeySynthesis.swift`, `KeySynthesis.parse`) resolves a key name into a virtual keycode + `CGEventFlags` (+ a Unicode string for printable characters): single printable characters, `Enter`/`Return`/`Space`, `Tab`, `Escape`, `Backspace` (kVK_Delete 51) / `Delete` (kVK_ForwardDelete 117, matching web left/right-delete semantics), `Home`, `End`, `PageUp`, `PageDown`, arrows (`ArrowUp`/`ArrowDown`/`ArrowLeft`/`ArrowRight`), `F1`–`F12`, and `+`-joined modifier combos using `Control`/`Shift`/`Alt`/`Meta` (with `Ctrl`/`Option`/`Opt`/`Cmd`/`Command` aliases). Key- and modifier-name matching is case-insensitive; unknown keys/modifiers throw a clear `AXFailure` carrying a one-line category summary of what's supported (not 100 names). **Combo characters use real keycodes, not the Unicode path:** a bare printable character is delivered on the layout-independent `keyboardSetUnicodeString` path (keycode 0), but a character inside a modifier combo (e.g. `Meta+s`) resolves through a US/ANSI keycode table (a–z, 0–9, common shortcut punctuation) to a real physical keycode with no Unicode string — because keycode 0 is physically `kVK_ANSI_A`, a Unicode-only `Meta+s` could be read by an app (via the keycode or its `charactersIgnoringModifiers`) as **Cmd+A** and fire Select All when the hunt asked for Save. A modified character with no ANSI mapping (rare — accented letters, etc.) keeps the Unicode fallback. Shortcut letters in combos therefore assume a US/ANSI physical layout — the standard synthesized-keystroke trade-off, documented in the README. `Session.press` (`Commands.swift`) keeps the deterministic, focus-independent **AXPress fast path** for a bare Enter/Return/Space *when the resolved element advertises the press action* (new `axSupportsAction` helper in `AX.swift`), and otherwise takes the **synthesis path**: activate the target app (`NSRunningApplication.activate`), best-effort focus the resolved element (AX `kAXFocusedAttribute`), then post `keyDown`/`keyUp` built with `CGEvent(keyboardEventSource:)` and delivered via `CGEvent.postToPid(_:)` **targeted at the attached app's PID** so keystrokes can never land in whatever is frontmost; printable characters ride on `keyboardSetUnicodeString` for keyboard-layout independence. No new TCC prompt — CGEvent posting is already covered by the existing Accessibility grant. The TS `MacDriver` (`src/browser/mac-driver.ts`) is unchanged: it forwards the hunt's key string (modifier combos included) verbatim, so the Swift helper is the single source of truth for the supported set. **No macdriver version bump on this branch** — the pinned `MACDRIVER_VERSION`/helper pin is bumped at release time per `macdriver/RELEASING.md`; this helper change ships with the next `macdriver-v*` release. Coverage: 18 new pure-parser Swift tests (`macdriver/Tests/ProwlMacDriverCoreTests/KeySynthesisTests.swift` — full mapping table, Backspace/Delete distinction, case-insensitive keys and modifiers, bare printable-char unicode path, the modified-letter→ANSI-keycode path and its divergence from the bare-char path, the modified-non-ANSI unicode fallback, shortcut punctuation, modifier combos + macOS aliases, multi-modifier combos, literal `+` key, the AXPress activation-flag predicate, and the unknown-key/unknown-modifier/empty-key error paths) alongside the 11 existing helper tests (29 `swift test`, green; `swift build -c release` green); a new TS passthrough test in `test/mac-driver.test.ts` pins that the driver forwards `press` keys verbatim. macOS target **stays experimental**. README updated (macOS step-compatibility notes + the `press` step reference: full key vocabulary, PID-targeted synthesis under the existing Accessibility grant, clear errors for unknown keys). TS build + lint clean; 1055/1055 tests pass. **Not verified here**: live key-synthesis against a real macOS app is the owner's dogfood step (per the repo's no-live-app policy).

## ~~PROWL-050 / ARCH-004: Hunt-level assertions on the macOS path~~
**Resolved**: 2026-09-01 (branch macos-assertions)
**Description**: The native run path (`executeNativeHuntAttempt` in `src/runner/index.ts`) hardcoded `assertions: []`, silently discarding every hunt- and config-level `assertions:` block on the macOS, Android, and iOS targets. It now calls a new `evaluateNativeAssertions` (`src/runner/assertions.ts`) after the steps complete. Because all three native targets share one run path (`executeNativeHuntAttempt`), the fix lands on **macOS, Android, and iOS uniformly** with the target named in every message/result. **Applicable subset** — `selectorExists` / `selectorNotExists` — is evaluated against the session driver's `count()` (the same driver query the inline `assert` steps use); a failing applicable assertion fails the hunt. **Web-only types** (`urlIncludes`, `urlEquals`, `noConsoleErrors`, `noNetworkErrors`) are reported per-assertion with a new `AssertionResult` status `"skipped"` — visible in `result.json`, in `summary.md` as `[SKIPPED]`, and in JUnit as `<skipped/>` with a `skipped=` count — never silently dropped and never a hard error. **Semantics mirrored from the web path** (the deliberate choice from PM decision 1): assertions run *after steps complete even when a step failed*, and run status is `stepFailed || assertionsFailed ? "fail" : "pass"` — identical to `executeHuntAttempt`. Config- and hunt-level blocks merge with the same `mergeAssertions` the web path uses. **Warning refinement:** since `noConsoleErrors`/`noNetworkErrors` default to `true` in config, mirroring the web merge naively would emit two "web-only skipped" console warnings on *every* native run (alert-fatigue). So the console warning naming the target is emitted only for the web-only assertions a **hunt explicitly authored** (clear intent, e.g. `urlIncludes`); the config-default console/network checks still surface as `skipped` results (fully auditable) but do not warn — this matches the PM's own examples (the warning example was `urlIncludes`; config-level `noConsoleErrors` was specified only as "must not hard-error"). The pre-flight `assertHuntAssertionsSupportedByTarget` reject was removed from the top-level native run; it is retained as the guard for **sub-hunt** (`runHunt`) assertions, which are never evaluated on any target (top-level-only concept) and so are still hard-rejected on native to avoid a silent drop. Tests: new direct `evaluateNativeAssertions` unit tests (applicable pass/fail, web-only skipped, warn-only-for-authored, config-default-skipped-without-warning) and rewrites of the three native runner tests (macOS: applicable-pass + web-only-skipped visible in result.json/summary.md, and applicable-fail failing the hunt; Android: second-native-target applicable-runs + web-only-skipped; iOS: failing applicable assertion fails the hunt). README gained a hunt-level assertion compatibility matrix in the macOS Target section, cross-referenced from the Android/iOS sections and the assertion reference. Build + lint clean; 1048/1048 tests pass.

## ~~PROWL-054 / BUG-MAC-001: Back-to-back macOS runs attach to the terminating previous instance~~
**Resolved**: 2026-08-16 (branch fix-macos-launch-race)
**Description**: First real-usage bug for the macOS target (found by Sentwise dogfooding). Back-to-back `prowl run` invocations could attach to the *previous* instance while it was still terminating: `quit()` only *requested* termination and returned immediately, and `launch()` picked up any running instance of the bundle id with no `isTerminated` filter — so the next run attached AX to the dying process's still-readable tree, clicked a zombie menu, then hung forever waiting for a window no living process had been asked to open (aggravated by hunts ending with the status menu open, whose NSMenu tracking runloop delayed clean termination). Fixed entirely in the Swift helper lifecycle (`macdriver/Sources/prowl-macdriver/Commands.swift`), no timing heuristics: `quit()` now cancels any open status-item menu (extracted `dismissOpenStatusMenu()`, also reused by `closeMenu()`), requests terminate, polls `isTerminated` to a deadline, escalates to `forceTerminate()` if it doesn't go quietly, and only returns once the process is actually gone — reporting the outcome (`terminated` / `forced` / `alreadyGone` / `timedOut`) in the quit response. `launch()` resolves only a live (non-terminated) instance to reuse; if only terminating instances remain it waits (bounded by the launch timeout) for their PIDs to clear before launching fresh (`awaitLaunchableInstance`), and verifies the resolved PID is still alive before returning success. A fake-helper test (`test/mac-helper.test.ts`) covers the new `{ quit, state }` response shape (teardown still closes the client on a non-clean quit); 669 tests pass (from 668 pre-branch), lint + tsup/DTS build green, and the Swift helper builds `swift build` debug + release. Live re-verification with real back-to-back runs is the user's job (no GUI automation in tests).
